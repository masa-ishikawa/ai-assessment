# AI Assessment

The generator's output is the reference for both assessment content and slide composition. This skill contains its own lightweight Oracle base, authoring rules and verification workflow. Preserve the generator deck's appearance as closely as possible while correcting clipping and overlaps locally.

## Output filename

- Name customer-facing PPTX files `<会社名>御中_<製品名>_AI活用ご提案.pptx`, using the current assessment company and service/product names. Preserve the legal company name; remove an existing trailing `様` or `御中` before adding `御中` once. Sanitize filesystem-invalid characters. Do not append dates or internal version labels unless requested.
- Apply this convention both to default generator output and the final Oracle-restyled deliverable in `output/final/`. An explicit user-supplied filename or `--output` path takes precedence.

## Default visual design

- Use the warm color variation by default: warm white, charcoal text, Oracle red, terracotta and muted gold, with pale warm panels. The shared palette is `ai_assess_runtime/presentation_theme.py` in the active repository.
- Use deep warm-brown headers with white body panels for representative-theme comparisons. Keep evaluation labels unboxed. On cost pages use a deep warm-brown total band, a pale table header, subtle alternating rows and unboxed assumption notes. Total amounts use the same 14pt size as body/table text; never enlarge them for emphasis.
- Preserve slide content and composition. Use square cards, thin borders/top rules, warm table headers and subtle alternating rows. Avoid unrelated blue/green/purple category colors and monochrome-only styling.
- The native generator applies this design before Oracle restyling; retain its body colors when applying the Oracle base. Preserve actual logos, cover/closing furniture, images, footer, editable text and font floors. A different palette requires a user request.
- Implement future design changes in the reusable drawing layer, never by customer name, slide number or copied customer artifacts.

## Source of truth

- This skill is the single user-facing entry point for AI assessment work. Use `generate_assessment.py` and its active runtime behind the skill; do not present old customer decks, generic validation decks, or customer-specific build scripts as alternative workflows or deliverables.
- Reuse `generate_assessment.py` output: assessment JSON, research log and corresponding PPTX. Preserve the logical slide order, page grouping, columns, tables, diagrams, emphasis and information density—not just its text.
- Read [references/oracle-authoring.md](references/oracle-authoring.md) for the contained Oracle authoring and verification rules. Use this skill's [assets/base.pptx](assets/base.pptx) as the brand source. Its three pages are cover (1), body (2), and closing (3); use these page numbers in the restyling plan. Preserve their actual masters, layouts, background, logo, title and footer. Generator body compositions take priority over selecting a different completed example. A separately installed `oracle-ppt-creator` skill is not required; if present, leave it installed.
- Keep the original generator, runtime, Excel parser, authentication and OCI configuration frozen unless implementation changes are explicitly requested. Running the unchanged content pipeline or `--from-json` renderer is allowed. Rendering an existing JSON establishes the composition reference without new LLM/Web generation.

## Portable repository execution

- Locate the cloned project from the current Codex workspace: use its root, or walk upward until both `generate_assessment.py` and `.agents/skills/ai-assessment/SKILL.md` exist. This also works when this skill was copied into a user-level skills folder. If the clone is not open, ask the user to open it. Do not use a developer-specific absolute path.
- Before Python assessment or restyling, use an available Python 3.12+ interpreter to call `scripts/run_assessment.py`. On macOS use `python3` or `python3.12`; on Windows use `py -3.12` or `python`. The runner creates `.venv` and installs `requirements.txt` on first use. `generate`, `fill`, `restyle` and `revise` are runner subcommands; preserve the generator's CLI arguments after the subcommand.
- Example: `python scripts/run_assessment.py generate <input.xlsx-or-txt> --json-only --output-json <review.json>`. For the Oracle pass, use `python scripts/run_assessment.py restyle <reference.pptx> <candidate.pptx> --plan <plan.json>`; the runner supplies this skill's base PPTX.
- If no suitable host Python exists but Docker or Podman is available, use the repository's `Containerfile` to run the same Python generator and restyler with mounted input/output paths. OCI credentials remain external. Use an available native presentation renderer for visual review.

## Natural-language entry point

- Treat a request such as `○○な会社の○○なサービスについてAI assessを実行` as authorization to complete the full assessment workflow. The user does not need to prepare Excel when the company, product/service, business description or official URL can be identified from the request and public sources.
- When the request supplies only a company name, product/service name or URL, confirm the official identity and current product scope from public sources, then create a reproducible UTF-8 text input under the active project. Record the company, target service, supported business scope, known data, stated AI intent, source URLs and explicitly unknown items. Do not invent private system facts, installed database versions, customer data volumes or agreed PoC conditions.
- Use the company and product/service named by the user as the assessment boundary. If several products have similar names, resolve the best-supported official target from the supplied context and public pages; ask the user only when multiple materially different targets remain plausible.
- Continue from the text input through Web/LLM research, assessment JSON generation, strict validation, PPTX rendering, Oracle authoring and visual QA. A request to `実行` is not complete after creating an input file, research log, JSON or generator reference deck; deliver the reviewed PPTX under `output/final/` together with the reviewed JSON and research log.
- Apply the same reusable workflow to every customer. Do not copy another customer's claims, sources, use cases, selected themes or technical assumptions into the new assessment.

## Workflow

1. Read [input-and-evidence.md](references/input-and-evidence.md). Identify the target company and product/service from the user's natural-language request, supplied URL or existing input. Create the supported text input automatically when no Excel/TXT exists. Locate any requested content and appearance references. An existing generator PPTX from another customer may illustrate the composition; its claims and use cases must not enter the target customer's content.
2. Inspect the source PPTX visually, alongside its JSON and research log. For new content, use the existing Excel/text content pipeline. If the target has JSON but no PPTX, run unchanged `--from-json` into a private build directory to obtain the reference.
3. Follow [slide-plan.md](references/slide-plan.md). Map source pages to output pages, normally one-to-one. Keep the generator's grouping and approximate placement: preserve a three-column comparison, a one-page PoC, or a left-diagram/right-explanation page as such. Do not expand a source deck into a new narrative merely to expose every nested JSON field.
4. Save a separate authoring plan with source paths/hashes, page/shape mapping and local edits. Preserve source JSON/PPTX and logs. Keep all 15 AI use cases on one editable slide with unchanged IDs and selected PoCs.
   - Move directly from the 15-use-case catalog to three representative AI technology approaches. Do not add an intermediate shortlist of five or show non-selected cases as hold/next-stage items. Score all candidates on business value, feasibility, data readiness and scale readiness, then select one eligible candidate from each previously unused primary modality before filling any remaining slot by score. Use forecasting/anomaly ML, optimization/ranking, grounded RAG, document understanding and generative assistance as modality families. Do not force a low-readiness modality merely to create variety; when fewer than three eligible modalities exist, fill the remaining positions by the base score. A customer-specified or fixed-catalog selection takes precedence.
   - Title the selection page `15のAIユースケースから整理した AI技術アプローチの代表3テーマ`. Show the common evaluation viewpoints and, for each representative theme, why it is representative, the point to confirm in the PoC and the preparation point. Continue directly into the three technical detail pages.
   - Lay out the three representative-theme cards from the longest generated copy, keeping all three cards equal in width and height. Give each body block enough fixed vertical space for PowerPoint's Japanese line wrapping, and keep a visible gap before the next heading. Widen the card text area and extend the cards toward the footer-safe boundary before reducing text; preserve at least 14pt. If a bottom handoff band competes with the card copy, express that transition in the lead sentence and use the recovered space for the cards. Verify the first, longest and last cards in native PowerPoint.
   - Keep the opening sequence stable: cover, AI assessment explanation, management-plan analysis when verified, industry/current-trend analysis, business-impact bridge, then the 15-use-case catalog. The two industry/value slides are always present; a verified management plan adds one page immediately before them. Do not insert a separate assessment-overview page.
   - Infer the end-user industry from the input customer profile, users and business processes; do not treat the assessed vendor’s product category as the industry. Research three concrete AI adoption developments in that industry, with publication timing, actual business use, implications for the assessed service and visible source URLs. Keep the assessed vendor’s product announcements and management plans on their own pages; market-size forecasts alone are not industry AI adoption evidence. Save the industry inference, selection decisions and source excerpts in the research log. Use the same gray 9pt source-URL format at the bottom of both industry/current-trend and management-plan pages, above the inherited footer without overlap. Render the following business-impact bridge as three independent cards with current decision issue, AI-enabled change, KPI and an effect formula. Keep unsupported improvement rates or amounts out of these cards.
   - Omit the separate `既存システムとAI・OCIの役割分担` slide. Move directly from the three technical detail pages to the OCI architecture slide.
   - Center each representative-theme number horizontally and vertically in a text box matching its circle. For costs, align the total label and amount on a common vertical center, and position the assumption notes below the actual table bottom with a gap and footer clearance.
   - Show OCI cost estimates in yen by service and in total, using comma-separated integer amounts such as `92,854円／月`. Do not round service costs or totals into approximate ten-thousand-yen labels.
   - Write all customer-facing slide text in a calm, collaborative proposal tone. Avoid forceful negative or directive endings such as `〜しません`, `〜してはならない`, `禁止` and `必須です`. Prefer affirmative phrasing that explains the intended approach, such as `〜を想定しています`, `〜が考えられます`, `〜を基本とします`, `〜を参考情報として扱います` and `〜を確認しながら進めます`. Keep factual, quantitative and safety conditions precise while presenting them as evidence, choices and review steps.
5. Apply the Oracle base to the source compositions using an isolated, reusable authoring path. [scripts/restyle_pptx.py](scripts/restyle_pptx.py) preserves native source body objects while applying actual Oracle template furniture. Its plan records inspected source and template pages plus local shape edits; do not infer these IDs from another deck without inspection.
6. Fit text by repairing the affected box, spacing or wrapping, with faithful shortening when necessary. Preserve each page's visual hierarchy. Editable body/table/card/diagram text is at least 14pt. The single 15-use-case catalog may remain 12pt, and source URLs on the industry/current-trend and management-plan pages use 9pt. Inherited header/footer furniture retains its settings (normally 10pt). Disable shrink-to-fit below these minimums and reflow the affected page. Do not flatten slides into images. Preserve original illustrations; identify existing raster diagrams honestly rather than claiming their labels are editable.
   - Omit the presenter name from the cover by default, including names inherited from the Oracle template. Retain company, service and affiliation. Show a presenter only when explicitly requested for the current deck.
   - Use `AI Use Case Assessment` as the cover and introduction title, without an OCI prefix. Place `<formal company name>様のAI構築をご支援` beneath the introduction title in dark 16pt text, normal weight. Preserve the legal company name and avoid duplicating honorifics. Keep a visible gap before the three explanatory blocks and preserve the photo and band. Keep OCI product names in technical content.
   - End the management-plan page with a concise `AI活用方針` or `AI活用の方向性` summary of how the assessed company should use AI based on the displayed strategy connections. Use only the existing input and analysis; do not introduce new claims. Keep source caveats in the research log rather than a visible caution band.
   - For presentation-only refinements, reuse the latest reviewed deck and research. Adjust spacing, alignment, line breaks and faithful wording without regenerating the assessment or changing its cases, priorities, figures or technical design. Automated test execution follows the project AGENTS.md and the user’s explicit preferences.
   - Treat the management-plan comparison and three-theme selection pages as fixed-height layouts. Before rendering, shorten each editable body field to the space it has: use a single concise sentence per comparison cell where possible, then a separate short related-theme line only when needed. In the three-theme cards, retain the reason / PoC confirmation / preparation headings and keep each answer to about two Japanese lines at 14pt. If content still competes with the next heading or the footer-safe area, shorten it faithfully or enlarge the text region within the existing composition; do not reduce the font below 14pt or rely on shrink-to-fit.
   - Preserve the agreed composition of the three AI-technology-theme detail pages unless the user explicitly asks to redesign them. The standard composition is: two explanatory lines below the title, a five-step horizontal flow, a three-column implementation table, and one bottom note. Keep its geometry, color assignment, spacing and information hierarchy; update the text inside those regions. Title the pages `AI技術テーマ n／3｜<theme>`.
   - Build all three priority-use-case detail pages from the actual Oracle body-slide root used by the surrounding pages. Retain the base slide's title, `sldNum` and `ftr` placeholders in that root, then import only the technical body shapes. Do not insert a completed technical slide after Oracle restyling, and do not repair a missing footer by adding standalone page-number or copyright text boxes. If any detail page lacks the inherited placeholders, rebase the whole page from the Oracle body slide before delivery. Remove generator-specific footer shapes and verify slides immediately before, within and after the three-page sequence in native PowerPoint. The page number, copyright position and inherited 10pt footer settings must match the surrounding body pages.
   - Treat a request to make these pages more technical as a content change. Put the technical design into the existing regions instead of replacing the page with a new card or lane layout. The two opening lines show implementation summary and input data; the five-step row shows preparation, AI processing, result creation, return to the existing screen/API and human confirmation; the table shows data/AI processing, logical database objects, existing-system connection, deployment choice and controls; the bottom note explains the deployment choice.
   - Each implementation-design page must show: input data and scope; two to four applicable Oracle Database or OCI AI capabilities; processing steps; logical database objects such as input views, feature/vector indexes, result tables and audit logs; results returned to the existing screen or API; and the execution/control boundary.
   - Accept technical fields returned as either text or arrays and normalize them into ordinary presentation text. Use familiar short names such as `OML4SQL`, `DBMS_SCHEDULER` and `ORDS` when long names would obscure the design. Do not display Python/JSON array syntax.
   - Select technical patterns from the use case rather than the customer name. Forecasting, anomaly detection, scoring, ranking and optimization use Oracle Machine Learning plus SQL/business constraints. Knowledge search and question answering use Oracle AI Vector Search and grounded RAG, with Select AI or OCI Generative AI where supported. Document extraction uses an appropriate multimodal extraction path and stores normalized results and review history in Autonomous AI Database. Other cases use only capabilities supported by their data and process.
   - Treat product names, database versions, table names, volumes and installed options as input-dependent. Never hard-code a company, product or industry. When deployment facts are unknown, show the choice between execution in an existing Oracle Database and offload to Autonomous AI Database through copied test data, Database Link or API, with version, volume, authorization and latency as decision factors.
   - Do not invent physical table or view identifiers. If the generated result contains unconfirmed identifier-like placeholders, replace them with logical object roles based on the use-case modality.
   - Keep selection rationale, broad business value and go/no-go discussion on the catalog, comparison and measurement pages. Do not repeat them as the main content of the three technical pages. Do not introduce `保留` or `開始・見送り条件` into the technical-page table.
For an existing deck revision, use [scripts/revise_pptx.py](scripts/revise_pptx.py) with a reviewed page/shape edit plan; preserve unrelated package parts and the 12pt catalog. When the introduction uses a photo across the right half with an overlaid band, the photo and band must share the same left and right boundaries; fill the region without distorting the image.
7. Review content/evidence fidelity, XML relationships, native editability and layout. Compare the output with the generator reference and inspect every output slide in PowerPoint using PNG or direct viewing. Final artifact is PPTX only. Record discrepancies and material limitations separately; do not invent missing numbers.
   - Set the PPTX core document title from the actual cover title and subtitle. Do not retain `AI Use Case Assessment Sales Session` or other metadata from the Oracle base. Export a temporary PDF and confirm that its PDF `Title` matches the customer-facing assessment title.
8. Deliver the reference-faithful baseline before further design changes. Keep QA records and reproduction commands outside customer-facing slides and notes. Verify frozen source hashes when reporting no generator changes.
   - Save the requested customer deliverable under `output/final/`. Do not create or offer an unrelated named-company PowerPoint merely to prove generic behavior; use automated fixtures and structural checks for that purpose.
   - Treat the repository's `old/` directory as a historical archive. Do not execute or import code from it, use its decks as current templates, or deliver its files unless the user explicitly requests historical inspection.
